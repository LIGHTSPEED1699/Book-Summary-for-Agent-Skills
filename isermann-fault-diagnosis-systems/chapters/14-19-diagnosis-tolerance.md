### Ch14 — Comparison and Combination of Fault-Detection Methods (lines 7135-7260)
- 14.1 assumptions common to model-based FD: residual must show a "significant change" — offset after fault large enough AND lasting long enough vs inherent stochastic character; exact process-model agreement never holds, so KIND and SIZE of model discrepancy is primary interest; all methods require a mathematical model.
- Table 14.1 (qualitative comparison, linear processes; columns: parity equations | state observer | output observer | parameter estimation):
  - model structure: exactly known (first three), known (PE); model parameters: known, constant (first three) vs UNKNOWN, time-varying (PE); disturbance models for unknown inputs: exactly known (all); noise tolerance: small/small/small vs medium (PE).
  - stability of detection scheme: no problem / depends on design (state observer) / no problem / no problem.
  - excitation by input: "additive faults: no, multiplicative faults: yes" — identical for all four columns.
  - detectable faults: abrupt / drift / incipient / single faults = YES for all four methods. multiple faults: SISO no, MIMO yes (parity + both observers) vs SISO yes MIMO yes (PE).
  - fault isolation: parity MIMO yes; state obs MIMO yes; output obs MIMO yes; PE SISO yes MIMO yes.
  - additive faults: yes for all; MULTIPLICATIVE faults: no for parity and both observers, YES only for parameter estimation.
  - robustness to parameter changes: problematic (parity, both observers) vs UNPROBLEMATIC (PE).
  - nonlinear processes: many classes possible (parity), limited (observers), many classes possible (PE); static processes: yes (parity), no (both observers), straightforward (PE).
  - computational effort: small/medium (parity), medium (observers), medium/larger (PE).
  - closed loop: yes for parity/observers; PE "yes, external excitation".
- Method-character bullets (verbatim gist): parity eqs: model known & well-fitting, especially additive faults, multi-outputs required, very fast reaction to sudden faults, online real-time for fast processes. Observers: same list plus "if not too many observers required" and "observers have very similar properties as parity equations"; design-dependent stability. PE: structure known, especially MULTIPLICATIVE faults; additive input/output faults also detectable; several parameter changes uniquely detectable from ONE input + ONE output; very small changes detectable (slow AND fast developing); online possible even for fast processes; input excitation required for dynamic process parameters.
- Conclusions (near-verbatim): parity vs observers almost identical properties, but parity equations much SIMPLER to design, implement, understand, and easily expanded to nonlinear processes; both well suited for additive, NOT in general for multiplicative faults; parameter estimation BEST for multiplicative/parametric faults; some additive faults can be modeled as unknown parameters; PE with dynamic models needs dynamic input excitation, for static processes only measurements at different operating points.
- Essential difference: parity/observers need MORE THAN ONE output to detect+isolate several faults; PE one input + one output suffices to detect AND diagnose different faults.
- Abrupt-fault speed: state estimation and parity react faster than basic PE (PE averages out disturbances over time); PE with forgetting factor or dynamic state model for parameters (Kalman-filter-type estimator) CAN follow abrupt parameter changes ON COST of disturbance rejection; state estimation tradeable the same way -> abrupt-following is a DESIGN choice for both.
- Fault modeling caveat: many real faults are multiplicative; additive models apply to some sensor and actuator faults (see Sec 5.2.3) — assumption choice strongly influences all methods.
- 14.2 suitability: SISO -> PE primarily recommended for multiplicative faults incl. actuator/sensor dynamics changes (static additive sensor/actuator faults fold into parameters); state observers usable when faults map into observed states (example: pipeline leak detection); output observers and parity equations RATHER LIMITED for SISO: only ONE residual -> no isolation of different faults. SIMO/MIMO: analytical redundancy grows -> advantageous for parity + output observers, residuals can be made independent of certain inputs/faults -> isolation possible; counterweight: precise MIMO models with all cross-couplings hard to obtain.
- 14.3 combination (since each family has complementary pros/cons; parameters usually unknown anyway -> apply parameter estimation FIRST):
  - 1. Sequential PE + parity eqs: PE obtains the model; parity equations do cheap online change detection; PE on request for DEEP fault diagnosis.
  - 2. Sequential PE + state estimation: PE obtains model; state estimation for fast change detection; PE on request for deep diagnosis.
  - 3. Parallel PE + state estimation: covers multiplicative AND additive faults; depends on input excitation.
  - 4. PE + vibration analysis: PE for parameter-mapping faults; vibration analysis for unbalance, knocking, chattering — especially attractive for rotating machines.
  - Choice depends on process, faults, allowable computational load; integrating process-model-based + signal-model-based methods gives good overall info; combination generates the most relevant analytical symptoms for integrated diagnosis. Fig 14.1 scheme = parity equations online/real-time detect, thresholds exceeded -> trigger PE near real-time for deeper diagnosis (SVF = state variable filter if required).

### Ch15 — Fault-Diagnosis Methods: Diagnosis Procedures and Problems (lines 7255-7401)
- 15.1 task definition: diagnosis = determine fault TYPE with max detail — size, location, time of detection; based on observed analytical + heuristic symptoms plus heuristic process knowledge (Fig 2.7, 15.1: feature extraction + change detection for both measured and human-observed variables; unified symptom representation before diagnosis).
- Vocabulary: FEATURES = extracted values from signal/process models describing process status (parameters, states, parity errors, residuals); SYMPTOMS = unusual changes of features from normal/nominal; fault-free case: symptoms = 0.
- Fact inputs to knowledge-based diagnosis: (a) analytical symptoms sg_i = limit checking + model-based + change-detection outputs; (b) heuristic symptoms = operator observations (acoustic noise, oscillations, colors, smoke) representable only qualitatively via linguistic terms "little/medium/much"; (c) process history & fault statistics (running time, load, last maintenance; SPC fault frequencies) — vague, so treated as heuristic; (d) unified symptom representation: confidence numbers 0 < c(s_i) < 1 (probabilistic/reliability-theory style) OR fuzzy membership functions 0 < mu(s_i) < 1 — both put analytical + heuristic symptoms in one 0..1 range; data string fields: number, name, value, reference value, confidence/membership, detection time, explanatory text [15.1].
- (e) Fault-symptom relationships: physical propagation fault -> (intermediate) events -> symptoms; DIAGNOSIS = inversion of causality, which is NOT reversible / ambiguous — chains cannot be reconstructed from data alone; intermediate events often invisible -> structured knowledge from inspection of faulty behavior must be included [15.2]. If NO causal info: trained classification (Ch16, unstructured knowledge base); if causalities expressible as if-then rules: reasoning/inference methods (Ch17); Fig 15.3 survey.
- 15.2.1 knowledge representation: (1) ANALYTIC knowledge from physical laws/quantitative measurements (physical fault-symptom relations for rule-based inference, or measurements aggregated indirectly into classification parameters); (2) HEURISTIC knowledge not explicitly written, learned experimentally/trial-and-error, from operator & engineer experience; forms: rules, frames (object-oriented), predicate logics, directed graphs (esp. networks and tree structures); inference via forward/backward chaining.
- 15.2.2 prior knowledge: physical parameters p_phys have functional relationship to model parameters: theta_model = f(p_phys), eq (15.1) [image, not decoded; reconstructed form] — often only characteristics (monotonicity) known; example: DC-motor rotor resistance depends on temperature (not a model parameter) -> overheating indicated by high resistance estimate; also prior info about similar/independent faults structures the diagnosis system; use ALL usable prior knowledge.
- 15.2.3 statistical symptom distributions: data-driven diagnosis sees two symptom types: estimated model-parameter changes + output/measurement deviations (residuals); (15.1) frequently MULTILINEAR theta_model = sum c_i * p_phys,i (c_i constants) [reconstructed] or locally approximated as such; physical-parameter changes -> MULTIPLICATIVE deviations of model output vs measurement -> determines typical symptom distribution of multiplicative faults; distributions can favor/hinder specific classifiers [15.2].
- 15.2.4 data size: statistically sufficient fault data often unavailable (faulty systems dangerous/expensive, artificial faults forbidden; simulation only an inadequate substitute); high-dimensional symptom spaces -> extremely sparse data ("curse of dimensionality"); DC-motor diagnosis built from 21-D symptom space [15.2]; automatic diagnosis-building algorithms must handle sparsity.
- 15.2.5 symptom representation: four data types [15.5]: binary; multi-valued (ordered like small/medium/large -> convertible to metric; unordered -> code as set of binary variables); interval-scaled (e.g. "50%", practically ~ metric); metric. Binary coded 0/1 and treated as metric OK unless too many artificial binaries destabilize algorithms (e.g. clustering). Solution: represent ALL variables as fuzzy sets (Fig 15.4: single membership function per increasing/decreasing symptom vs five linguistic ones — one-FM version cheaper; handles both human and numerical input [15.3]); risk: projection to membership values loses information -> choose FMFs carefully (Ch17).
- 15.3 exercises: DC-motor symptom split analytical/heuristic (armature resistance increase, vibrations, brush fire color, smoke, torque/speed drop, temperature); build fault-symptom TREE for faults: too-large current, brushes w/o solid contact, plugged cooling channel, bearing fault; solenoid actuator knowledge; thermocouple symptoms.

## Isermann Ch16-17 — Pattern Classification & Diagnostic Trees/Process Models

### Ch16 Fault diagnosis by classification (pattern recognition), lines 7402-7694
- Framing (Ch15/16 bridge, ~7376-7401): separate n_f faults; fault vector F, symptom vector s. Nearly all methods compute a fault measure f_i per fault class F_i; decision = max f_i, but ALL f_i values matter — noise/unclear situations raise several f_i at once, signaling uncertain decisions. Ch15+16 = two main classes: classification WITHOUT structural knowledge (Ch16) vs inference WITH structural knowledge (Ch17).
- 16.1 Problem statement: if no structural symptom->fault knowledge, learn reference symptom vectors s_i,ref for each fault F_i experimentally (training), then compare observed s. Classifier = mapping symptom space -> fault-measure space, outputs f_i in [0,1]; desired binary targets c_i in {0,1} (NN target-value terminology; for NN training the f_i become targets). A maximum operation after classification yields the diagnosis. Method taxonomy (Fig 16.3): statistical (Bayes), density-based (geometrical), approximation (polynomial), AI (decision trees, fuzzy, artificial neural networks); historical order same.
- 16.2 Bayes classification: assume class-conditional densities p(s|F_i), commonly Gaussian with covariance Sigma and centers s0_i; maximum-likelihood fits (centers = mean of reference data); alternatives: recursive estimation, Bayes inference. Minimum wrong decisions = select max posterior p(F_i|s) via Bayes law; denominator p(s) is a normalizer, irrelevant for comparison. Prior p(F_i) matters: estimate from occurrence frequency in labelled data; if undeterminable assume uniform (equal fault probabilities) unless experience says otherwise; well-chosen priors improve diagnosis "substantially" — do not underestimate. Gaussian assumption breaks with overlapping fault areas [16.7]. Nonparametric option: histogram estimate of p(s|F_i); needs lots of data; variable-size-grid histograms for scarce data, converging toward geometric classifiers.
- 16.3 Geometric classifiers: class membership from distance to labelled reference points s_i,k. Nearest-neighbor: take class of reference point with minimum Euclidean distance to s_j. Drawback: overlapping classes + sparse references -> rough, sub-optimal decision boundary. k-nearest-neighbor: voting among k closest points = local parameter-free density estimate (class with highest relative frequency in hypersphere around s; radius governed by reference-data density). Storage of all reference points is the classic objection; modern hardware relieves it; condensed nearest-neighbor selection reduces stored points [16.9].
- 16.4 Polynomial classification: approximate posteriors by polynomials f_i(s) = g(s, a_i), params a_i = [a_i0 a_i1 ... a_i,n_i], max #terms = combinatorial in order o and n_s [formula OCR-lost; reconstruct: (o+n_s)!/(o! n_s!)]. Fit by least squares V_i = sum over N reference pts (f_i - t_i(k))^2 with 0/1 targets t_i(k) (class of reference data known, so target probs are 0/1). Use: evaluate one polynomial per class, take max. Decision boundary: locus f_1(s) = f_2(s), generally a polynomial of same order o. Error linear in parameters -> direct (pseudo-inverse) solution; for Gaussian diagonal-cov data all methods (pseudo-inverse, gradient descent, perceptron) coincide and match Bayes-optimal boundary. o=1 = linear discriminant technique (statistics/medical dx), solves linearly-separable problems; hyperplane from f_i = 0.5. Typical orders o = 1..3. Term-selection pitfalls: too many terms -> overfitting/poor generalization; too few -> inflexible; linearly dependent W columns -> numerically infeasible normal equations. Two selection principles: (1) greediness in reducing V_i; (2) linear independence (most independent terms first); remove (nearly) dependent terms always. Implement via Gauss-Jordan [16.16], Orthogonal Least Squares [16.14], SVD [16.15]; selection also reveals inappropriately chosen/meaningless symptoms — aids symptom design and complexity reduction.
- 16.5 Decision trees: origin social sciences/botanical classification; series of binary questions subdividing data set S0 into S11/S12 by decision D1 recursively; stop when a leaf set is pure (single class); leaf carries class label; query = walk from root to leaf. Example Fig 16.7a: two faults F1/F2 with two continuous symptoms s1, s2, binary threshold decisions; tree can be incomplete (uneven branches); Fig 16.7b shows the resulting axis-aligned space partition.
  - Construction without expert knowledge: single-step optimal strategy — pick decision maximizing subset "purity"; minimize impurity = entropy index H = -sum P_i log P_i over next level [formula OCR-lost; standard Shannon form], P_i replaced by relative frequency.
  - Tree growth = decisions extracting most information from the sample; a pure leaf contains no information.
  - Gini index = alternative impurity measure (1 - sum P_i^2, OCR-lost formula): faster (no log), behavior nearly identical; both symmetric about P=0.5, vanish for pure sets, max impurity at P1=P2=0.5.
  - Greedy: single-step optimal, NOT globally minimal tree (global optimum computationally infeasible); growing + pruning heuristics trade structure complexity vs classification performance to avoid overfitting.
  - Continuous variables: theoretically infinite candidate decisions; discretize by interval techniques (compute time not the real problem).
  - Real weakness: one-step-only optimality — a split that does not reduce entropy at level 1 may allow a much lower average entropy at level 2; beneficial to sometimes proceed anyway.
  - Uni-variate decisions -> axes-orthogonal splits; can approximate any boundary but needs many decisions/large trees; works best with weakly correlated inputs; multivariate splits exist but combinatorial explosion makes them hard.
  - Common in medical diagnosis because intuitive, trustworthy, understandable.
- 16.6 Neural networks: MLP + RBF are static universal function approximators (any function to arbitrary accuracy if structure large enough), vs Bayes which parameterizes a fixed Gaussian form. Train weights w to minimize sum-of-squares J. Trained with same 0/1 targets as polynomial classifier -> they approximate class-conditional posteriors.
  - Key result [16.3]: at optimum w*, network output = conditional average E{t_i | s} = integral t p(t_i|s) dt; with binary targets & n_f outputs this collapses to y_i(s) = P(F_i|s) — network outputs = Bayesian posteriors, i.e. can learn statistically optimal decision boundaries without assuming a pdf shape. Caveat: only if true minimum w* found (sufficient size, no overfitting, convergent optimizer).
  - Usage stats: ~half of classification-based diagnosis publications used NN [16.10]; likely >half today; decent results with moderate design effort.
- 16.6.1 MLP: inputs = one per symptom, one output per fault; outputs are probabilities -> sigmoidal activation in OUTPUT layer (unusual: identification uses linear last layer). Hidden layer: weighted sum + bias a_ji, activation y(.); projection removes irrelevant input info -> good for high-dim problems, but high input dim -> many free parameters -> needs big reference data base. Use MLP when class boundaries are complex AND lots of data; nonlinear optimization -> longer training, but modern algorithms fine; multiple hidden layers trainable fast. Variant [16.25]: one net per fault vs nominal — smaller nets, simpler functions, but more total parameters. Direct measurements->faults mapping [16.2] skips symptom generation: only for simple static systems; throws away designer domain knowledge; breaks fault-detection/diagnosis nomenclature.
  - Big MLP flaw: extrapolation. Global activation functions respond over whole input domain -> trained for complex boundary, outputs unpredictable far from (even near) training data; acute in sparse high-dim input spaces; first formulated [16.11]; remedy = local approximators (RBF).
- 16.6.2 RBF: non-normalized basis functions + singleton output layer; output weights LINEAR in error -> deterministic single-step optimization (Sec 9.3.3); research focus = basis-function placement. Standard: cluster input data, centers at cluster centers (k-means, Kohonen feature maps) — both minimize distance data->reference vectors, iterative, UNSUPERVISED (ignore class labels) -> overlapping classes may share one basis function -> output layer alone can't separate. Fixes: constructive algorithms add basis functions driven by performance (e.g. [16.6], LOLIMOT [16.14]); decision-tree pre-segmentation: learn uni-variate decision tree, place one basis function per segment -> superior to the tree alone. Alternative: over-supply then prune — global ridge regression adds regularization term w·sum(w_l^2) to LS error [16.11]; irrelevant weights -> 0, prune neurons one at a time with re-optimization -> compact net.
  - RBF vs MLP extrapolation: local basis functions -> new/uncovered symptom points activate nothing, outputs ~0 = automatic rejection ("new situation, no definite conclusion") — avoids wrong diagnosis instead of guessing; enables on-line growth: add basis function when point too far from known classes [16.4]. Local weights interpretable: second-layer weights ~ smoothed posterior estimates p(F_i|s) via (16.19).
  - Applications: industrial plants [16.17], chemical reactors [16.20][16.22], two-link manipulator [16.21]. RBF good with many reference points (last-layer optimization efficient), less critical optimization behavior, but more parameter storage than comparable MLP.
- 16.6.3 Clustering / self-organizing maps as classifier [16.5]: UNSUPERVISED, assume nearby symptom-space points share fault class; competitive neighborhood search finds clusters; then label each cluster by majority class of members; classify = assign cluster label. Weaker than supervised NN (class info unused during structure/weight adaptation), struggles with overlapping classes. Valuable as INITIALIZATION: RBF center placement, initial fuzzy membership functions.
- 16.7 Problems (4): compare a-priori assumptions Bayes vs geometric vs polynomial (use Fig 16.5); geometric vs decision-tree differences; NN input/output variables for diagnosis; which method when very few symptom data per fault.
- Ch17 chapter opening sits INSIDE Ch16 line range (7671-7694): title "Fault diagnosis with inference methods". Partial causal knowledge fault -> events -> symptoms; causal network Fig 17.1a (nodes = states, edges = relations); knowledge organized as IF(condition) THEN(conclusion) rules; premise = symptoms s_i facts, conclusion = events e_m and faults f_i; multiple symptoms combined with AND/OR connectives (Fig 17.1b fault-symptom tree). Causalities from fault-tree analysis FTA (faults -> intermediate events -> symptoms, physical) or event-tree analysis ETA (symptoms -> faults, diagnostic forward-chaining) [17.31, Sec 4.2].
### Ch17 Fault diagnosis with inference methods, lines 7671/7695-8361

- 17.1 Fault trees: graphical directed graphs for reliability + diagnosis, binary relationships; fault situation at top, symptoms/conditions below; elements = logic connections, events, symptoms; Fig 17.2 scheme for binary symptoms/states [0,1]. Hierarchical structure aids human comprehension; common in safety-critical analysis. Quantitative failure probabilities computable by combining element failure probabilities through the tree -> system failure probability; used early in design to find critical subsystems. Diagnosis use (e.g. industrial robot [17.5][17.16]): one tree per fault F_i, leaves = the n_s symptoms; ideal decision = binary evaluation per tree. Reality: symptoms uncertain/not clearly recognized -> binary evaluation fails; naive workaround = pick the tree whose activation is most easily reached by flipping leaf statuses = essentially pattern matching to nearest known fault pattern; extract then argues this view suggests abandoning laborious tree matching for a different procedure [line truncated at 2000 chars in extraction, OCR cut — exact next step lost]. Boolean parallel/serial equations for rule premises don't succeed because faults/symptoms are continuous [17.5][17.16]; timing extensions [17.34], timed discrete-event-system model-based detection [17.52][17.56][17.53].

- 17.2 Approximate reasoning: for continuous processes with continuous symptoms, binary decisions inadequate; use heuristic process models + weighting of effects; forward/backward strategies; diagnostic goal = fault decision specifying TYPE, SIZE, LOCATION + time of detection [17.25][17.26]. History: engineering (reliability: nuclear, aerospace, electrical) grew from FTA [17.12][17.24][17.5...]; AI offered cause-effect handling [17.43] + diagnostic problem solving [17.36][17.44][17.45][17.58], first medical then technical, heuristic symptoms; later higher abstraction levels treating causalities as deep-logic interdependencies [17.47][17.30]. Synthesis: engineering fault-symptom trees + AI causal strategies; model-based (analytical) symptoms from Ch8-11 detection enable DEEP diagnosis pinpointing physical fault origins (roots).
- 17.2.1 Forward chaining: modus ponens — match facts (symptoms s_i) to premises, draw conclusions -> candidate faults F_i via heuristic causalities. Symptoms uncertain -> represent as confidence c(s_i) or fuzzy membership mu(s_i) in [0,1] (unified form Sec 15.1; fuzzy intro Ch 23.3).
  - (a) fuzzy reasoning: multi-level fuzzy rule system built from ETA-derived fault-symptom tree (Fig 17.6, two rule levels, max/min ops, singleton inputs). Symptoms = fuzzy sets s_i^(k) with linguistic labels ("normal", "less increased", "much increased"). Mamdani implication + compositional inference [17.63][17.35][17.64][17.13]: match facts to premises -> fit degrees; fuzzy AND/OR via t-norms/t-conorms; conclusion via max-min composition (premise fulfillment clips conclusion fuzzy set); accumulate multiple rules contributing to one output by union; defuzzify (center of gravity, maximum-height, mean-of-maximum) — but for diagnosis defuzzification often replaced by simple MAX operation = most possible fault.
  - max/min wastes info (only extremes kept) -> prod-sum operations: AND = product, OR = sum [17.x, formulas OCR-lost; standard algebraic t-norm/conorm], all values represented; similar to probability formulas. NOT: 1 - mu in both cases.
  - System dimensions: n_s symptoms x P levels x N rules per level x n_f faults -> can blow up even for small processes -> implementation matters. Two reasoning procedures:
    - Horizontal (sequential): activate rules level l -> l+1; match symptoms to level-1 premises -> events e_(2); match events level l -> level l+1; match final events to fault fuzzy subsets f_i; accumulate -> global possibility per fault; decision = maximal possibility; defuzzify -> crisp fault SIZE.
    - Vertical (multiple, all symptoms -> all faults at once): chain s_j -> e -> f via multiple composition of relations into overall matrix R (fuzzy relational equation, Eq 17.6, proposed [17.61][17.60]); solve F = s ∘ R; accumulate; max possibility; defuzzify. Defuzz after each level optional.
  - [17.29]: earlier variant with derivatives of measured variables as symptoms, F = s ∘ R* (Eq 17.7) from FTA knowledge -> must solve INVERSE problem (find F given s), e.g. Sanchez operator [17.48]; [17.21] post-mortem diagnosis via (17.6), near-binary events as causes, also inverse. Practical note: knowledge acquisition usually starts with FTA (faults -> events -> symptoms, Fig 15.2b); if knowledge complete, build forward form directly -> inverse problem circumvented, standard fuzzy tools usable.
  - Simplifications for compute cost: singleton symptoms (matching -> direct fuzzification of crisp values); singleton event/fault conclusions (conclusion height = premise fulfillment); universal-set conclusions (same height, but size of event/fault then undeterminable). With singletons/universal sets the whole procedure = aggregation of facts via t-norms/t-conorms + chaining results [17.25]. Extension to time-dependent faults: incipient, intermittent, multiple faults [17.60].
  - (b) simplified fuzzy logic for diagnosis (Fig 17.7): output is not an arbitrary fuzzy set but a fault MEASURE in [0,1] (gradual possibility): symptom far from linguistic pattern -> ~0; perfect match -> 1. Consequence reduced to singleton scaled by rule fulfillment -> no output membership functions, NO defuzzification needed.
  - (c) probabilistic fault-symptom reasoning: assign P(s_i) to symptoms, P(e_i) to events/faults; simplified Bayesian network from causal tree with conditional probabilities (17.43). Assuming symptoms mutually independent and independent of events: AND connection = product of probabilities, OR = [prob form OCR-lost; 1-prod(1-p) expected]; if events certain P(e)=1: AND = prod P(s_i), OR = [OCR-lost]. Formulas mirror fuzzy prod-sum ops but independence assumption ignores the causal structure of fault-symptom trees — caveat.
- 17.2.2 Backward chaining: modus tollens — assume conclusion (event/fault) known, search relevant premises; useful when symptom set incomplete. Workflow: forward-chain with known symptoms -> display candidate events/faults to operator -> pick most plausible as hypotheses -> backward-chain by asking for the MISSING symptoms -> restart forward chaining; interactive dialogue, repeat until operator terminates [17.15][17.16]. Other strategies: Establish-Refine, Hypothesize-and-Test, depth/width search [17.22]. If forward reasoning used all symptoms, backward reasoning serves to VALIDATE diagnosed faults [17.61]. Until now symptoms assumed simultaneous/static; further cases: dynamically developing (incipient/intermittent) faults -> dynamic fault trees [17.41][17.60]; multiple faults.

Loose combos (NN maps membership functions; NN supplies MF parameters; fuzzy base automates NN design heuristics e.g. #hidden neurons; serial/parallel hybrids [17.3]) exist, but "hybrid neuro-fuzzy" in narrow sense = NN and fuzzy engine NOT separable — structurally equivalent, one network whose layers each map to a linguistic operation, i.e. simultaneously a fuzzy inference system and a NN; fuzzy rules extractable from trained weights. Rule-learning survey: [17.37][17.8].
  - 17.3.1 Generic structure (Fig 17.10): fuzzification layer -> neural layer(s) implementing rule logic (t-norm "AND" as product/min units) -> rule activations -> defuzzification. Distinguish:
    - Regression: output = continuous y=f(x); defuzzification via output MFs or singletons + weighted sum (singletons == center-of-gravity defuzz). Rules: IF s AND e THEN y (fuzzy attribute / linear function).
    - Classification (diagnosis): inputs s_i, outputs f_i (fault measures), n_f-dim binary 0/1 target scheme (class 3 -> output 3 = 1, rest 0); hard decision = maximum over RULE ACTIVATIONS (strongest rule activation = classification). Often the max op is omitted/deferred: keeping rule activations lets you judge reliability of the max decision from runner-up activations. Classification rules have no output fuzzy attributes; max acts on premise activations; strongest conclusion = statement. Most regression concepts translate to classification.
  - Mamdani-type hybrids: FALCON [17.32] maps Mamdani rules; layer tasks linguistically understandable; NO connectionist weights storing info (all unit links; MF params = effective weights into defuzz layer); not fully interconnected like MLP; rules with identical conclusions OR-combined. [17.46] same structure for neuro-fuzzy diagnosis (only diff: max as OR); FALCON for incipient motor-fault diagnosis [17.2]. NEFCLASS [17.39]: triangular MFs, MinMax inference, alternative weighted-sum t-conorm (weights fixed 1) in last layer = plain summation of rule activations as OR. SARAH [17.3]: ANDOR neuron — parametric composite of bounded difference (t-conorm) and bounded sum (t-norm), parameter theta continuously interpolates AND<->OR; sigmoidal approximation -> resembles standard sigmoid perceptron; Gaussian antecedent MFs; output layer: rule activation scales output singleton -> crisp value.
  - Takagi-Sugeno hybrids: consequence = linear/nonlinear function of inputs (no fuzzy attribute); most frequent linear consequence; overall output = weighted sum of consequences. ANFIS [17.28]: inputs used twice (fuzzification + consequence), Gaussian-exponential MFs, product t-norm, 4th layer normalizes membership functions. LOLIMOT [17.40]: similar but multi-dimensional MFs (ANFIS = grid-based with explicit AND), different learning. TS systems mainly regression/nonlinear modeling: multiple-model fault detection + generation of NONLINEAR PARITY EQUATIONS [17.4][17.33][17.51]; not typical classifiers but usable as local polynomial classification systems for diagnosis [17.19].
  - 17.3.2 MF identification: uni-variate MFs => grid segmentation of input space (interpretable); multi-dim MFs => general segmentation, better performance, worse understanding. Three construction principles: (1) manual (grid or, better, prior knowledge/visual inspection/physical insight; set MF params to optimally separate classes); (2) concurrent rule+MF construction (input-domain splits; not detailed here); (3) batch data-based — mainly clustering (unsupervised input-space clustering [17.3][17.42][17.59], assumption: nearby points share class; cluster center = MF prototype, point spread = MF width). Most frequent algorithm: Fuzzy-C-Means (FCM) [17.6]. Error-based refinement of MFs added during training in any case.
  - 17.3.3 Rule identification (MFs predefined): problem = combinatorial rule explosion — complexity grows exponentially with input dimension, but real problems are much smaller; at most ~50-100 rules should suffice for typical technical diagnosis; beyond that transparency (the whole point of neuro-fuzzy) is lost -> highly complex problems belong to other algorithms. With n_s symptoms each with n_a attributes: #premises = n_a^n_s; #rules = n_f * n_a^n_s; limited to p premise terms -> binomial blowup [formulas OCR-lost]; concrete: 5 attributes, 10 symptoms, 3 faults ~= 30 million possible rules [text says "relatively moderate case... about 30 million"].
    - SBE (start with ALL rule combinations, eliminate inapplicable): feasible only for few symptoms (explosion). SARAH Hebbian learning: matrix R rows=premises x cols=n_f, all rules initially possible, elements 0; iterate training data; compute all MF memberships -> premise activations; strongest activation wins; strengthen (increase by increment) the R entry matching the strongest output attribute; iterate over all data; then threshold decides kept/discarded rules. [17.32] variant for FALCON: act directly on connection weights instead of explicit matrix. General idea = "activated learning": find concurrent input/output activations, strengthen/create matching rules, reduce contradicting competitors, threshold to prune.
    - SFS (start empty, augment rules): criteria for choosing/adding and stopping distinguish variants; same redundancy/contradiction checks as SBE. Driver: iterate data points, or minimize overall error. Data-driven variant scales with #data points (vs SBE's rule space) -> small-but-high-dimensional data sets feasible. NEFCLASS: process a new data point only if no existing rule covers its input/output relation (points with new info); activation strength decides if a new rule is justified; learning criteria "simple" (best overall data point) vs "best per class" [17.38].
    - Concurrent rules+MFs: driven by overall least-squares error; keep creating rules/MFs (segment input space, place local basis functions) until error good enough. Neural Gas [17.17]: add RBF centers at highest-error locations. LOLIMOT: recursive input-domain splitting creates fuzzy segmentation concurrently [hard to interpret linguistically, like RBFs]. Hyperbox approach [17.1]: fit each class data into hyperboxes; on overlap, subdivide overlapping region into smaller boxes until no overlap; project boxes -> fuzzy attributes.
  - 17.3.4 Optimization: same toolbox as NNs. Least-squares objectives -> parameters entering output linearly = trivial (RBF-equivalent structures e.g. LOLIMOT with singleton/linear output layers). Layer-1/2 params (MF params, relevance weights) need nonlinear optimization: FALCON backpropagates into membership layer (LS objective from output f vs target t per data point); NEFCLASS tunes MF params only, SELECTIVELY: one pattern at a time, each rule unit with output error > 0 backpropagates error to its rule neuron; since conjunction = min, the dominating MF = smallest activation; adjust only that MF's params up/down per error sign. [17.32]: parameter optimization easier than classical NNs because clustering initialization gives good starting point. SARAH: all params optimized, unconstrained backprop [17.3]. ANFIS: consequence (linear-function) weights via single-step pseudo-inverse; antecedent params via gradient descent. LOLIMOT antecedents (MSF positions) found by simple iterative splitting instead. Transparency conditions for rule interpretation (from [17.19]): MF selection, local behavior, weight constraints, small rule base.
- 17.3.5 SELECT (SELF-learning CLASSification Tree) [17.20][17.19]: fuses decision-tree ideas + NN adaptation + fuzzy interpretability. Basic element (Fig 17.12): fuzzification layer -> weighted sum of membership values fed to a neural AND-operator (approximated bounded-sum / ANDOR with alpha=1, soft conjunction: output near 1 even if not all inputs are 1). Rule output: o_i = sigma(lambda*(sum_j w_ji*mu_j - 0.75*n_p)) [17.18 reconstructed from text: threshold 0.75*n_p chosen empirically for fuzzy AND; lambda = slope = "degree of fuzziness", large lambda -> binary; sigmoidal approximation]. Connections carry RELEVANCE WEIGHTS w_ji (interpretable); fuzzy attribute per symptom chosen from n_a(s_i) candidates (one MF per rule premise, abridged notation in book).
  - Tree structure (Fig 17.13): tree of AND-operator nodes, leaves = rule consequences; multiple leaves may share a conclusion; conclusion degrees of fulfillment a_i^(rule) combined by t-conorm (max) -> fault measure f_j output. Sequential evaluation: after top neuron output o^(1), next node activation multiplied by (1-o^(1)), continued down the chain so the sum of all rule activations never exceeds 1 (prioritizes earlier, more general rules); for large trees this multiplication is switched OFF (sigmoid ~0 at small activations would make products vanish).
  - Why SFS not SBE: many faults x many symptoms but few experiments -> sparse symptom space; and most faults distinguishable by only 1-2 significant symptom reactions -> adaptive complexity per decision difficulty. Learning = iterative training-set reduction (flowchart Fig 17.14): design MFs -> candidate rule selection -> rule evaluation -> add neuron -> remove correctly classified data -> repeat until training set empty / no useful rule / predefined complexity.
  - MF design in SELECT: any 17.3.2 method ok; manual if prior knowledge. Default: FCM on 1-D projection of each symptom works well enough; for nonuniform symptom distributions a modified Degressive FCM (nonlinear transform of cluster memberships [17.19]) gives finer clusters near zero ("symptom not reacting") and broader toward range limits; then merge adjacent strongly overlapping clusters. MF functional form: product of two sigmoidals (4 params: two inflection points + two slopes) = asymmetric, simple; edge attributes = single sigmoidals [17.20, formula OCR-lost]. FCM -> MF params: hard-assign each point to max-membership cluster center v_m; estimate std dev of assigned points (formula OCR-lost); satisfy (a) membership >= 1-eps at center (eps~0.03), (b) pairwise MF intersection at "Bayes limit" = point where the two neighboring Gaussian pdfs take equal value (book text "same value 0.5" [OCR?]) -> attributes already good class separators, no normalization needed.
  - Candidate rule selection: translate training set from numeric symptoms to fuzzy attributes (each point -> argmax MF). For each fault F_j build rule R_j starting from ONE premise: pick the symptom whose most-frequent fuzzy attribute value within class F_j data covers most of that class ("IF s3 large"). Evaluate; if not satisfactory extend premise by one AND-term ("AND s5 small") up to p_max. Keep best rule R*; it becomes a new neuron; correctly classified data removed (shrinks subsequent rule extraction); repeat. Learning ends when set empty / no useful rule / p_max reached. Result: sequential rule tree.
  - Rule evaluation: threshold delta on rule output defines classified subset -> four subsets: correct-Fj (N...), correct-not-Fj, false-positive, false-negative [cardinalities OCR-mangled]. Decision-tree style entropy idea: compare impurity before/after rule. [17.55] proposes a cardinality-product measure (Eq 17.23, OCR-lost) maximizing (correct pos + correct neg) style sums — SYMMETRIC so unusable: also maximized by a rule firing for everything EXCEPT F_j. Plus simpler heuristic: difference of mean rule fulfillment between class-Fj data and all other data (Eq 17.25, OCR-lost).
  - Worked example (Fig 17.16): 2 symptoms x 2 fuzzy attributes x 3 fault classes. Initial candidates: R1 IF s2 small THEN F1; R2 IF s1 large THEN F2; R3 IF s1 small THEN F3 (17.26; set alone insufficient — just the starting menu). R2 evaluates best -> keep as R*, delete F2 data. Final rule set (17.27ish, OCR-lost) contains ELSE branches: IF... THEN... ELSE (IF ... THEN ... ELSE F3). Characteristics: most informative premises chosen first; smaller total complexity than a parallel rule base because the sequential "ELSE" chain hides complexity (complete parallel set for this problem would need more rules, Eq 17.28 OCR-lost).
  - Relevance-weight optimization (after rule extraction): fine-tunes each rule's covered region; optimizes weights of multiple inputs simultaneously -> captures symptom correlations that 1-D clustering missed. LS objective over fault measures vs 0/1 targets; optimization done PER AND-neuron (not all weights in parallel); training data reduced rule-by-rule exactly as during learning (correctly classified samples excluded); include the strong-fulfillment subset of the rule's own class plus other-class samples; drive rule outputs to 0/1. Interpretability constraints on w (Eq 17.29/17.30 OCR-lost; sum-to-unity mentioned with the linearized variant). Backprop with sigmoid derivatives; softmax used [17.7], details [17.19]. ## Isermann Ch18-20 — Redundancy/Fault Tolerance + DC Motor Case Study

### Ch18 Fault-tolerant structures (lines 8356-8467)
#### Reliability strategies (intro, before 18.1)
- Two approaches to improve reliability [18.4]: **perfectness** (avoid faults: better mech/electrical design, longer service life, regular maintenance + wearing-part replacement; early fault detection enables maintenance-on-demand instead of scheduled) vs **tolerance** (contain consequences: faults compensated so no system failure = fault-tolerance, cf. Sec 2.4).
- Fault-tolerance generally = **redundancy**: one or more extra modules connected (usually parallel), identical or **diverse**. Applies to hardware, software, information processing, mech/elec components (sensors, actuators, microcomputers, buses, power supplies).

#### 18.1 Basic redundant structures
- **Static redundancy** (Fig 18.1a): ≥3 parallel modules, same input, ALL active; outputs to a **voter** deciding by majority. TMR: wrong output of one module masked by 2-out-of-3 voting — single fault tolerated with NO specific fault-detection effort. n modules tolerate (n−1)/2 faults, n odd [text OCR'd "(7-1)/2 ... 7 odd" = (n−1)/2, n odd]. Voter itself can be made redundant [18.8]. Cons: high cost, power, weight; **cannot tolerate common-mode faults** (common fault sources hit all modules).
- **Dynamic redundancy** (Fig 18.1b,c): minimal config = 2 modules (operating + standby/back-up); fewer modules, more information processing. REQUIRES fault detection: simple methods use output only — consistency checking (signal range), comparison with redundant module, information redundancy (parity checking, watchdog timers). Then **reconfiguration** switches to standby and removes faulty unit.
  - **Hot standby**: standby continuously operating → small transfer time, cost = operational aging/wear-out of standby.
  - **Cold standby**: standby out of function, does not wear → needs 2 extra input switches + longer transfer time (start-up procedure). Fault-detection performance essential for both.
  - Extend to ≥2 standby modules to tolerate 2+ faults. **Hybrid** = static+dynamic combination, avoids both disadvantages at cost of complexity [18.8].
- **Software fault tolerance** (Table 18.1; table OCR scrambled, structure unreadable): static = repeated running (>3) of SAME software + majority voting — helps only transient faults; software faults are **systematic not random** → need **diversity** (different programming teams, languages, compilers); ≥3 diverse programs + majority voting. Dynamic software redundancy = **recovering blocks**: diverse backup software modules besides the main one [18.8],[18.5].
- **Duplex microcomputer for fail-safe** (Fig 18.2): two synchronized processors, outputs compared by two comparator software acting on two switches; disagreement → disconnect output from downstream. Covers hardware AND software faults but is NOT fault-tolerant (loss of output); useful when missing output = safe state — e.g. **ABS braking systems**.
- **Mechanical/electrical static redundancy** (Fig 18.3a): homogeneous/inhomogeneous materials (metals, fibers), lattice structures, spoke-wheels, dual tires, multiple wiring, multiple coil windings, multiple brushes for DC motors, multiple contacts for potentiometers. Inputs/outputs are forces/currents/energy flows, no voter — parallel elements take over higher load by physical laws of compatibility/continuity = **"stressful degradation"** (graceful). Examples: 2 gears/belts/chains/valves/hydraulic cylinders/power supplies, 2 motors at half load each; tandem-piston hydraulic brakes; double magnet ignition (aircraft); redundant kinematics [18.9].
- **Mechanical/electrical dynamic redundancy**: hot standby usually senseless (wear, idle power) unless transfer interruption must be avoided → mostly **cold standby** (Fig 18.3b). Fault detection from output measurands (position, speed, force, torque, pressure, flow, voltage, current) detects only large failures (complete breakdown); better if input + intermediate signals available. Pure mechanical (linkages, gears, chains) / pure electrical (amplifiers, cables, transformers) rarely measurable → dynamic redundancy mainly for **electro-mechanical** systems (speed/position-controlled motor units, electro-hydraulic, electro-mech actuators). Examples: standby feedwater pumps (steam boilers), backup power generators. Especially attractive for **mechatronic** systems (more sensors + embedded computers → process-model-based fault detection).
#### 18.2 Degradation steps
- Cost/space/weight force compromise; industrial/mobile/mechatronic (vs fly-by-wire) usually tolerate only **1–2 failures** for hazardous cases since safe state easier/faster to reach.
- Degradation vocabulary:
  - **fail-operational (FO)**: still operational after 1 failure; required when NO immediate safe state exists.
  - **fail-safe (FS)**: after failure component has safe state directly (**passive** FS, no external power needed, e.g. closing spring) or is brought there by special action (**active** FS, with external power).
  - **fail-silent (FSIL)**: after failure component stays externally passive (switches off), does not mislead other components.
- Vehicles: propose subdividing FO into "long time"/"short time". First check whether a safe state exists; for automobiles usually standstill/low speed at non-hazardous place; fail-safe status often = mechanical backup linkage for driver. Passive FS example: electronics fails, vehicle stops independent of electronics (throttle closing spring, driver via mech backup). No mech backup → only switching to still-working electronics brings moving vehicle to safe state = active FS, requires electric power availability.
- **Graceful degradation**: drop less critical functions to keep critical ones, by priorities [18.2].
- Table 18.2 fail behavior of electronic hardware (OCR garbled; reconstructed readings [reconstructed]): duplex (2 elements): static tolerates 0 faults → F; dynamic tolerates 0 → FO-F, discrepancy detection by 2 comparators + fault detection. Triplex (3): static tolerates 1 → FO-F; dynamic tolerates 2 → FO-FO-F. Quadriplex (4): dynamic tolerates 3 → FO-FO-FO-F. Duo-duplex (4): static tolerates 1 → FO-F.
- Design recipes: flight-control computers usually **triplex + dynamic redundancy (hot standby)** → FO-FO-FS: two failures tolerated, third lets pilot operate manually [18.7],[18.1],[18.6]. One fault tolerated staying FO (FO-F): triplex static OR duplex dynamic. FS after one failure: duplex with 2 comparators sufficient. FO then FS after next fault (FO-FS): triplex static OR **duo-duplex** (Fig 18.4) — duo-duplex advantages: simpler failure detection, modularity.
- Reliability numbers (Fig 18.5, [18.7]): single module (e.g. microcomputer) λ = 2·10⁻⁴ /h → MTTF = 5·10³ h; same modules as triplex or duo-duplex → λ ≈ 2·10⁻⁷ /h → MTTF ≈ 5·10⁶ h, i.e. **failure rate improved by factor 1000**.
- Problems (18.3): calc exercises — 2-out-of-3 static with modules+voter λ = 10⁻⁴/h; hot-standby duplex, modules+switch λ = 10⁻⁴/h, fault detection λ = 10⁻³/h; cold standby with inactive-module λ ≈ 10⁻⁵/h (value OCR'd as garbled "O-*[he*)" [OCR?]) — all ask for MTTF improvement.

### Ch19 Fault-tolerant components and control (lines 8463-8641)
- Intro: high-integrity systems need comprehensive fault tolerance across sensors, actuators, process parts, computers, communication (buses), control algorithms. Multiple-redundancy examples exist in aircraft/space/nuclear; cheap built-in-tolerance components for general applications still undeveloped.
#### 19.1 Fault-tolerant sensors
- Goal: at least **fail-operational for one sensor fault**, via hardware redundancy (same sensor type) or **analytical redundancy** (different sensors + process models).
- **19.1.1 Hardware sensor redundancy** (Fig 19.1): static = triplex + voter (19.1a); dynamic = ≥2 sensors + per-sensor fault detection (19.1b) — usually only **hot standby** feasible; weaker option = plausibility check of 2 sensors using signal models (e.g. variance) to pick the more plausible one (19.1c).
- Fault detection by **self-tests** (apply known measurement value to sensor) or **self-validating sensors** [19.10],[19.6]: sensor+transducer+microprocessor as integrated decentralized unit with self-diagnosis from several internal measurements; output = best estimate + **validity status: good / suspect / impaired / bad / critical**.
- **19.1.2 Analytical sensor redundancy** (Figs 19.2-19.3): reconstruct a redundant value from process models.
  - Scheme a: two measured outputs y1,y2 both depending on u (u unmeasured) → y1 reconstructed via models Gy1,Gy2 if no considerable disturbances. Scheme b: one output sensor + one input sensor → y1 reconstructed via process model Gyy1.
  - To get ONE fault-tolerant value with majority voting WITHOUT per-sensor fault detection, need ≥3 values of y1 (measured + two reconstructions) → combine schemes a+b (Fig 19.3a); sensor fault in y1 detected+masked by voter, replacement y2 or u-based estimate chosen by decision; single faults in y2 or u also tolerated.
  - Real example: **yaw-rate sensor of ESP** (electronic stability program, vehicles): steering wheel angle (input) reconstructs yaw rate via vehicle model (scheme b); lateral acceleration + left/right wheel-speed difference (no slip) reconstruct it (scheme a).
  - Generalized: 2 output sensors + 1 input sensor of equal quality → **3 residuals** via parity equations (or state observers, dedicated observers [19.5]) + decision logic → fault-tolerant outputs under single fault of any of the 3 sensors. All schemes assume ideal case; realizability needs constraints + extra filters.
  - Faulty sensor ideally **fail-silent** (switched off) but extra switches lower reliability. Rule of thumb: without per-sensor fault detection need **3 measurements** for one FO measurement; WITH in-built fault detection (self-test/self-validating) **2 suffice** (Fig 19.1b) — fault detection saves one element.
#### 19.2 Fault-tolerant actuators
- Actuator structure (Fig 19.4a): input transformer → actuation **converter** (energy form change, e.g. elec→mech) → actuation transformer → actuation element; typical chain DC amplifier + DC motor + gear + valve. Measurables: input ui, manipulated variable up, intermediate u3.
- Options: multiple complete actuators in parallel (static, or dynamic with cold/hot standby, Fig 18.1). Static example: fly-by-wire hydraulic actuators — ≥2 independent actuators + 2 independent hydraulic energy circuits.
- Partial redundancy at the least-reliable part: split actuation converter into parallel parts (Fig 19.4b "duplex drive"). Static examples: two servo-valves per hydraulic actuator [19.22]; three motor windings incl. power electronics [19.17]. SI-engine electromotor-driven throttle: only the **slider doubled** (static-redundant potentiometer position sensor, cf. Sec 20.2).
- Dynamic+cold-standby example: aircraft cabin-pressure flap actuator — two independent DC motors on one planetary gear [19.21].
- Cost/weight > sensors → prefer **FO duplex** actuators: both parts continuously active (static), hot standby, or cold standby; dynamic needs fault detection on actuator parts [19.14]; goal: faulty part fails **silent** (no influence on redundant parts).
#### 19.3 Fault-tolerant communication
- Fault-tolerant management systems need fault-tolerant bus between ECUs/sensors/actuators (nodes): multiple bus, hard real-time; minimum = **dual bus**, two independent buses + independent power supplies, all nodes on both buses, several nodes at least dual → multiple-access distributed real-time system.
- **CAN bus** (1983, automotive serial bus): event-triggered/asynchronous, priority by node identifier, **CSMA/CA**; usually only **soft real-time** (time behavior node-dependent, not guaranteed).
- **TTP (time-triggered protocol)** better for hard real-time drive-by-wire (sampling times ~ some ms) [19.9]: **TDMA** time slots → deterministic behavior; all nodes **fail-silent** (must detect faults in value AND time, go passive); guarantees via composability, periodic data transfer, fast fault detection, global clock sync [19.16],[19.31],[19.25],[19.9].
#### 19.4 Fault-tolerant control systems
- Feedforward: essentially all faults (small/large) affect outputs. Feedback: small additive/multiplicative actuator/process faults **automatically covered** by controller robustness = **passive fault tolerance** (no active measures); making controller very robust trades off control performance vs fault robustness. **Additive and gain sensor faults always break reference values** (also for feedforward). Faults exceeding robustness → too sluggish / too little damped / unstable → need **active fault-tolerant control** (Fig 19.5).
- Active FTC = fault detection + decision method + reconfiguration mechanism keeping operation acceptable (supervision loop, Fig 2.4). Reconfiguration may change: controller structure & parameters; used actuators; used sensors — accepting performance degradation. Key: severe faults detected fast+reliably, reconfiguration settled very fast → hard real-time demands.
- Literature: early work on aircraft/spacecraft reconfigurable flight control [19.26],[19.27],[19.18],[19.3],[19.4],[19.29],[19.7],[19.2]; summaries [19.1],[19.8],[19.28]; lateral-control application [19.30]. Survey [19.23]: four areas (fault detection, robust control, reconfigurable control, supervision), passive (fixed robust controllers) vs active (variable structure, fault-accumulation). Review [19.32] classifies by control algorithm (pre-computed vs online redesign) and application class: safety-, life-, mission-, cost-critical.
- Stability analysis has **three stages**: fault-free period, reconfiguration transient, post-reconfiguration steady state. Also important: input/state constraints, FDD uncertainties, reconfiguration delay, closed-loop identification, real-time. Most papers focus on algorithms, neglect overall architecture/technical platform → field immature, needs systematic research + practice.
#### 19.5 Automatic fault-management system
- Brings fault-tolerant sensors/actuators/communication/controllers together into an online, real-time **automatic fault-management system** (Fig 19.6). Five constituent modules:
  1. **Fault-tolerant actuators**: redundant identical or diverse actuators; inherently fault-tolerant actuators; actuator reconfiguration module.
  2. **Fault-tolerant sensors**: redundant identical/diverse; inherent tolerance; **virtual sensors** via analytical redundancy; sensor reconfiguration module.
  3. **Active fault-tolerant controllers**: redundant identical/diverse controller hardware; redundant **diverse software**; different controller structure/parameters — either pre-designed for a-priori-known faults or redesigned/adaptive after detection.
  4. **Fault-detection module**: uses normal closed-loop operating signals (parity equations, observers, parameter estimation); optional **test signals** periodically/on request to improve detection & diagnosis; indicates degree of impairment and safety criticality.
  5. **Fault-management module**: decisions from detection incl. impairment/safety effect; reconfiguration strategies: **hard or soft reconfiguration**, change of operating conditions (setpoints, process performance), switch closed-loop ↔ open-loop (feedforward).
- Worked logic (Fig 19.6 example, 2 manipulated + 2 controlled variables): normal actuator 1 fails (e.g. gets stuck) → actuator 2 (same type, or different with similar manipulation effect) takes over — duplex example: passenger cabin-pressure outflow valve [19.20]; aircraft additional control surfaces (ailerons/rudders) as redundant actuators. Sensor 1 totally fails → switch to same-type sensor 2 or analytical-redundancy **virtual sensor**: electrical throttle double potentiometer (Ch 20), model-based yaw rate from lateral acceleration + wheel speeds [19.12], horizontal+vertical gyro pair for aircraft bank angle [19.23]. Controller structure/parameters reconfigured to match.
- Also covers **process faults**: reconfiguration just selects actuator-sensor pair, adjusts controller 2 + reference w2. Example: fluid1/fluid2 heat exchanger — outlet temp of fluid 1 manipulated via fluid-2 **flow** instead of fluid-2 temperature.
- Fault-detection module: detect early in ALL components; **diagnosis not necessarily required** — reconfiguration only needs to know WHICH component failed, not cause.
- Controller adaptation: if reconfigured loop's transfer behavior known in advance → switch preprogrammed controller; if unknown → self-tuning/adaptive, but must be supervised + properly excited with perturbation signals [19.13] — problematic when very fast recovery required.
- Closed-loop caveat: fault detection must run under closed-loop conditions (Ch 12 problems). Risk: replacement controller + replacement sensor may not behave as expected → sometimes better to **drop to feedforward without output-sensor substitute** (performance loss but avoids instability) — real case: engine control, oxygen (A-) sensor fails → stoichiometric air/fuel ratio maintained open-loop from air-flow measurement + injected fuel-mass setpoint. Controller hardware/software faults detected per Ch 12, then new controller or feedforward.
- Conclusion: many possibilities, no general method — treat concrete cases. Closed-loop FDD + reconfiguration to redundant sensor demonstrated experimentally on electrical throttle valve actuator [19.24],[19.15].

#### 20.1.5 Fault diagnosis with SELECT (neuro-fuzzy, [20.1])
- **Symptoms (22 total)**: (i) windowed sums of |U_A|, |I_A|, |ω| (3); (ii) mean + std dev of the four residuals r1..r4 (and output residual σ?; list OCR-truncated) (≈8); (iii) **8 parameter-estimate deviations** from nominal, normalized, e.g. ΔR_A1 = (R_A,nom − R_A,est)/R_A,nom — index = which parity equation the estimate used (ΔR_A1, ΔL_A1?, ΔJ2, ΔJ3, ΔM_F2, ΔM_F3 pattern [subscript list OCR-mangled]); (iv) **2 estimation-quality symptoms**: recursive estimation variances σ_est,Ψ and σ_est,MF — fluctuating estimates ⇒ estimation-equation structure no longer valid ⇒ structural change detected.
